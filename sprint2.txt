40. QUEUE POLICY + CALLNEXT CONSISTENCY
Each CallNext transaction:
validates Window;
reads one committed QueuePolicy version;
stores those priority values in local transaction/application state;
selects candidate using those values;
claims candidate;
writes CALLED TicketEvent containing that same policyVersion and decisionPriority;
commits.
A concurrently committed QueuePolicy update may affect the next CallNext, but must not partially affect an already-running decision.

41. CONCURRENCY INVARIANTS
The following are mandatory.
Existing invariants
one Ticket
→ at most one assigned Window
one Window
→ at most one CALLED/SERVING Ticket
Service compatibility always enforced.

Appointment creation
Concurrent exact same idempotency request:
one Ticket
one publicNumber
one CREATED event
Other callers receive exact replay result.

Cancel vs claim
Cannot both mutate the same SCHEDULED Appointment successfully.
Final state is one of:
CANCELLED
or:
CALLED with one assigned Window
Never both.

Appointment claim
Two Windows racing for one Appointment:
at most one successful claim

QueuePolicy update
Two writers with same expectedVersion:

The other gets:
POLICY_VERSION_CONFLICT

Event atomicity
Every committed Ticket state mutation covered by Sprint #2 has exactly one corresponding event for that operation.
Idempotent no-op replays do not create duplicate events.
