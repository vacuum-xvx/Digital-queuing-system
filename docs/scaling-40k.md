# Архитектурное предложение масштабирования на 40 000 отделений

> [!IMPORTANT]
> **СТАТУС ДОКУМЕНТА: ARCHITECTURAL PROPOSAL / NOT MVP LOAD TEST RESULT**  
> Данный документ является концептуальным архитектурным предложением и проектно-расчетной моделью целевой распределенной системы на масштабах федеральной сети Почты России (40 000 ОПС).  
> Он **не является отчетом о синтетическом нагрузочном тестировании текущего MVP-стенда**, развернутого в локальном демонстрационном окружении.

## 1. Таблица количественных допущений (Quantitative Assumptions)

Ниже приведены исходные проектные допущения (*ASSUMPTION*) и расчетные нагрузки при линейном масштабировании на федеральную сеть:

| Параметр | Значение (*ASSUMPTION*) | Пояснение и формула расчета |
|:---|:---|:---|
| **Всего отделений (ОПС)** | 40 000 | Сеть почтовых отделений различного класса (от крупных ОПС до сельских). |
| **Окон обслуживания на ОПС** | 3 (среднее) | В среднем 3 активных окна операторов на отделение (суммарно 120 000 окон в сети). |
| **Рабочий день** | 10 часов / день | 36 000 секунд активной операционной нагрузки в сутки. |
| **Клиентов в отделении в день** | 100 талонов / день | Средняя суточная проходимость отделения: $40\,000 \times 100 = 4\,000\,000$ талонов/день в сети. |
| **Событий ЖЦ талона** | 4 события / талон | `CREATED` $\to$ `CALLED` $\to$ `SERVICE_STARTED` $\to$ `COMPLETED`: $4 \times 4\,000\,000 = 16\,000\,000$ транзакций/день. |
| **Средний Write RPS ядра** | ~444 RPS | Базовый поток записи: $\frac{16\,000\,000}{36\,000 \text{ с}} \approx 444 \text{ RPS}$. |
| **Пиковый Write RPS ядра** | ~1 350 RPS | Коэффициент пиковой неравномерности $k = 3.0$ в часы пик: $444 \times 3 \approx 1\,332 \text{ RPS}$. |
| **Read Short-Polling RPS** | ~26 700 RPS | Опрос состояния табло и мониторов (2 активных клиента/табло на ОПС каждые 3 с): $\frac{40\,000 \times 2}{3 \text{ с}} \approx 26\,667 \text{ RPS}$. |
| **Средний размер HTTP payload** | 1.2–1.5 КБ | Легковесный JSON (список активных талонов, статусы окон, вызовы). |
| **Полоса пропускания ЦОД** | ~320 Мбит/с | $26\,700 \text{ RPS} \times 1.5 \text{ КБ} \approx 40 \text{ МБ/с} \approx 320 \text{ Мбит/с}$ агрегированного входящего/исходящего трафика. |
| **Пулы соединений к БД** | 500–750 conn | 25–30 stateless-реплик бэкенда с `pgxpool.MaxConns = 25`, мультиплексированных через кластер PgBouncer к шардам. |

## 2. Естественное шардирование по отделениям (`branch_id`)

Очередь каждого почтового отделения абсолютно автономна:
* Вызов талонов оператором и поиск кандидатов происходят строго в границах конкретного `branch_id`.
* Транзакционные блокировки `FOR UPDATE SKIP LOCKED` действуют исключительно на строки одного отделения и не создают взаимных блокировок между отделениями.
* Целевое секционирование базы данных: таблицы `tickets`, `ticket_events` и `notification_outbox` секционируются по хешу отделения (`PARTITION BY HASH (branch_id)` на кластере шардов PostgreSQL с PgBouncer).
* Отсутствие межсегментных распределенных транзакций (No Distributed 2PC): любая мутация очереди затрагивает только партицию соответствующего `branch_id`.

---

## 3. Горизонтальное масштабирование бэкенда (Stateless Core)

* Узлы ядра бэкенда (Go Modular Monolith) не хранят разделяемого состояния в оперативной памяти (stateless-архитектура).
* Защита от состояния гонки обеспечивается на уровне ACID-транзакций базы данных.
* Экземпляры бэкенда масштабируются горизонтально в Kubernetes за балансировщиком нагрузки (Nginx / Ingress Controller), обеспечивая линейный рост пропускной способности.

## 4. Двухуровневая модель данных (Core + Edge) и правила разрешения конфликтов

### 4.1. Связность и требования в MVP
* **MVP-реализация**: требует постоянной связности с центральной БД (`PostgreSQL Primary`). Все операции (`POST /tickets`, `POST /operator/call`, `PUT /branches/{id}/queue-policy`) атомарно фиксируются в центральной базе.
* **Целевая архитектура (Edge Proposal)**: для удаленных ОПС с нестабильным каналом связи предусматривается периферийный агент отделения (Edge Agent), способный локально обслуживать зал при обрыве магистрального канала.

### 4.2. Правила разрешения конфликтов при восстановлении связи (Conflict Resolution)
В случае изоляции отделения и последующего реконнекта применяются строгие правила:

1. **Естественная граница владения (Natural Ownership Boundary)**:
   * Физическое отделение обладает исключительным монопольным правом на создание живых талонов (`LIVE`, `QR_ARRIVAL`) и перевод талонов по FSM операторами в зале.
   * Конфликт двойной мутации исключен физически: оператор ОПС №101 не может вызвать талон ОПС №202.
2. **System of Record (SoR) для очереди**:
   * Для операционного состояния очереди отделения (билеты, вызовы, завершение обслуживания) источником истины (SoR) является **локальное отделение (Edge)**.
   * При восстановлении канала накопленный локальный Transactional Outbox передает события в центральное хранилище Core методом дозаписи (Append-Only Event Stream) с сохранением строгого порядка оффсетов.
   * Центральная БД поглощает события идемпотентно по уникальному ключу дедупликации (`dedupe_key` / `event_id`) через `ON CONFLICT DO NOTHING`.
3. **System of Record (SoR) для глобальных справочников**:
   * Для глобальных сущностей (реестр отделений, справочник услуг, учетные записи персонала, глобальные политики очередей) источником истины (SoR) является **Центральный ЦОД (Core)**.
   * При восстановлении связи локальный Edge подтягивает актуальные версии конфигурации и политик из Core (`policy_version`).

## 5. Модель авторизации: MVP vs Target Enterprise ACL

> [!NOTE]
> **Авторизация в MVP**:
> В текущей версии MVP реализован ролевой контроль доступа (Role-Based Access Control, RBAC) на уровне системных ролей:
> * `employee` — оператор окон обслуживания;
> * `opc_chief` — начальник ОПС;
> * `client` — посетитель / клиент портала.
> 
> В MVP проверка прав валидирует роль в сессии пользователя (например, доступ к вызову талона разрешен только `employee`), но **не привязывает сотрудника жесткой матрицей ACL к конкретному отделению**. Это упрощает запуск демонстрационных сценариев и сквозное тестирование различных ОПС оператором тестового стенда.

**Целевая модель (Target Production ACL)**:
В промышленной эксплуатации Enterprise-контура вводится матрица разграничения доступа `(user_id, branch_id, role, window_id)` с запретом межфилиальных вызовов и интеграцией с корпоративным IdP/Active Directory.
