# Black-Box Тестирование и Верификация (Спринт №2)

## Описание
В данной директории расположен независимый тестовый модуль black-box верификации для **Спринта №2** системы цифровой очереди нового поколения (`tsifrovaya-ochered-novogo-pokoleniya`).

Тестирование осуществляется **исключительно по протоколу HTTP** против публичного API системы (`/health`, `/ready`, `/api/v1/*`), без прямого доступа к базе данных и без импорта внутренних пакетов домена, бизнес-логики или персистентности бэкенда (`backend/internal/*`).

---

## Соответствие замороженным контрактам (Sprint #2 Frozen Shared Contracts)
- **Только Black-Box HTTP**: взаимодействие с тестируемой системой происходит как с внешним сервисом.
- **Точные структуры DTO**:
  - `POST /api/v1/appointments`: заголовок `Idempotency-Key`, тело `{"branchId":"...","serviceId":"...","scheduledAt":"..."}`.
  - `AppointmentResponseDTO`: `{"ticket": TicketDTO, "scheduledAt": "RFC3339"}`.
  - `POST /api/v1/appointments/{ticketId}/cancel`: статус 200 OK, повторный вызов идемпотентен (200 OK), статус `CANCELLED`.
  - `GET /api/v1/admin/branches/{branchId}/queue-policy`: `{"branchId":"...","appointmentDuePriority":100,"qrPriority":10,"version":1,"updatedAt":"..."}`.
  - `PUT /api/v1/admin/branches/{branchId}/queue-policy`: тело `{"appointmentDuePriority":...,"qrPriority":...,"expectedVersion":...}` с оптимистической блокировкой версий (версия инкрементируется на 1).
  - `GET /api/v1/admin/tickets/{ticketId}/events`: `{"items":[{"id":1,"type":"...","fromStatus":...,"toStatus":"...","windowId":...,"policyVersion":...,"decisionPriority":...,"occurredAt":"..."}]}`.
- **Зафиксированные идентификаторы демо-стенда**:
  - Демо-отделение: `11111111-1111-1111-1111-111111111111` («Демо-отделение №1»)
  - Услуга «Посылки» (PARCELS): `22222222-2222-2222-2222-222222222222`
  - Услуга «Платежи» (PAYMENTS): `55555555-5555-5555-5555-555555555555`
  - Окно 1 (PARCELS): `33333333-3333-3333-3333-333333333333`
  - Окно 2 (PAYMENTS): `44444444-4444-4444-4444-444444444444`
  - Окно 3 (PARCELS): `66666666-6666-6666-6666-666666666666`

## Сценарии верификации

### 1. Foundation Regression Check (Перед и после прогона)
- Проверка `GET /health` возвращает `200 OK` (`{"status":"ok"}`).
- Проверка `GET /ready` возвращает `200 OK` (`{"database":"ok","status":"ready"}`).

### 2. Сценарий A — Создание записи и идемпотентность (Appointment Create + Idempotency)
- Создание талона предварительной записи на будущее время -> `201 Created`, статус `SCHEDULED`, источник `APPOINTMENT`.
- Повтор с тем же ключом идемпотентности и теми же параметрами -> `200 OK` (тот же талон, тот же `publicNumber`).
- Конфликтный запрос с тем же ключом, но другим временем или услугой -> `409 Conflict`, код `IDEMPOTENCY_CONFLICT`.
- Очистка: отмена талона, если он остался в `SCHEDULED`.

### 3. Сценарий B — Недоступность будущей записи для вызова (Future Appointment Not Eligible)
- Очистка окон.
- Создание предварительной записи с датой в ближайшем будущем (+6 сек).
- Выпуск обычного QR-талона в статусе `WAITING`.
- Вызов `call-next` из Окна 1 до наступления времени записи.
- Проверка: вызывается именно QR-талон, предварительная запись остаётся в `SCHEDULED`.
- Завершение QR-талона, отмена талона записи.

### 4. Сценарий C — Приоритет наступившей записи (Due Appointment Priority)
- Создание предварительной записи (+2 сек).
- Создание QR-талона до наступления времени записи.
- Ожидание наступления времени `scheduledAt` (+ запас 400 мс).
- Вызов `call-next` из Окна 1.
- Проверка: побеждает предварительная запись (статус `SCHEDULED` -> `CALLED`), несмотря на ожидающий QR-талон.
- Начало и успешное завершение обслуживания записи, затем вызов и завершение QR-талона.

### 5. Сценарий D — Маршрутизация по услугам (Service Routing)
- Создание наступившей предварительной записи на услугу «Посылки» (PARCELS).
- Окно 2 («Платежи») вызывает `call-next` -> `409 Conflict`, `NO_ELIGIBLE_TICKETS`.
- Окно 1 («Посылки») вызывает `call-next` -> `200 OK`, талон записи назначен.
- Завершение обслуживания.

### 6. Сценарий E — Отмена записи (Cancel)
- Создание предварительной записи.
- Вызов `POST /api/v1/appointments/{ticketId}/cancel` -> `200 OK`, статус `CANCELLED`.
- Повторный вызов отмены -> `200 OK`, статус по-прежнему `CANCELLED` (идемпотентность отмены).
- Проверка очереди: отмененная запись никогда не вызывается окнами (`call-next` возвращает `409 NO_ELIGIBLE_TICKETS`).

### 7. Сценарий F — Конкуренция отмены и вызова (Cancel vs Call Concurrency)
- Создание наступившей предварительной записи.
- Одновременный конкурентный вызов:
  - Горутина 1: отмена записи (`POST /appointments/{ticketId}/cancel`)
  - Горутина 2: вызов из Окна 1 (`POST /call-next`)
- Допустимые исходы:
  - Исход 1: отмена выигрывает (200), вызов получает 409 NO_ELIGIBLE_TICKETS, талон `CANCELLED`.
  - Исход 2: вызов выигрывает (200), отмена получает 409 INVALID_TICKET_STATE, талон `CALLED`.
- Проверка: талон гарантированно не может оказаться одновременно `CANCELLED` и назначенным окну.

### 8. Сценарий G — Конкурентный вызов двумя окнами (Appointment Double Claim)
- Создание одной наступившей предварительной записи на «Посылки».
- Одновременный вызов `call-next` из Окна 1 и Окна 3.
- Проверка: ровно один запрос возвращает `200 OK` с назначением талона, ровно один запрос возвращает `409 NO_ELIGIBLE_TICKETS`.
- Завершение обслуживания победителем, оба окна возвращаются в спокойное состояние (`204 No Content`).

### 9. Сценарий H — Версионирование политики очереди (Policy Versioning)
- Получение текущей политики `GET /admin/branches/{branchId}/queue-policy`.
- Обновление с актуальным `expectedVersion` -> `200 OK`, номер версии увеличивается на 1.
- Повторное обновление с устаревшей версией `expectedVersion` -> `409 Conflict`, `POLICY_VERSION_CONFLICT`.
- Восстановление исходных параметров политики с использованием актуальной версии.

### 10. Сценарий I — Журнал событий талона (Event Log)
- Полный жизненный цикл записи: создание -> вызов -> начало -> завершение.
- Проверка журнала `GET /admin/tickets/{ticketId}/events`:
  - Строгая последовательность: `CREATED` -> `CALLED` -> `SERVICE_STARTED` -> `COMPLETED`.
  - Событие `CALLED` обязательно содержит `policyVersion` и `decisionPriority`.
- Жизненный цикл отмены: создание -> отмена.
  - Журнал содержит `CREATED` -> `CANCELLED`.
- QR-поток: проверка сохранения генерации событий жизненного цикла для обычных QR-талонов без регрессии.

## Требования к повторяемости и недеструктивная очистка
- **Запрет на сброс базы данных**: автоматический запуск **НИКОГДА** не использует `docker compose down -v`.
- Все талоны корректно переводятся через публичные вызовы в терминальные статусы (`COMPLETED`, `CANCELLED`).
- Параметры QueuePolicy обязательно восстанавливаются к дефолтным (`appointmentDuePriority=100`, `qrPriority=10`).
- Сьют успешно проходит многократно подряд (Run 1, Run 2, Run 3) на одной и той же базе данных без потери данных.

## Инструкция по запуску

### Запуск через Go Test
```bash
cd qa/sprint2
go test -v -count=1 ./...
```
С указанием адреса тестируемого сервиса:
```bash
BASE_URL=http://localhost:8080 go test -v -count=1 ./...
```

### Запуск автономного CLI-раннера
```bash
cd qa/sprint2
go run ./cmd/runner -base-url=http://localhost:8080 -repeat=3
```
Параметры:
- `-base-url`: URL бэкенда (по умолчанию `http://localhost:8080` или переменная окружения `$BASE_URL`).
- `-repeat`: число повторных прогонов подряд без сброса БД (по умолчанию `3`).
